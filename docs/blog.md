# Give a model more time to think—without more tokens

LatentForge is built around one falsifiable idea: a model can perform repeated computation by refining a hidden numerical state rather than verbalizing every intermediate step. The question is deliberately narrower than a marketing claim: what changes when we give a model more time to think without giving it more tokens to think with?

The artifact makes that question executable. Its default task is a bounded line-navigation sequence, `1,0,1,1`, whose independent reference answer is `4`. A deterministic, untrained local recurrent substrate encodes that task, forms `h₀`, applies one shared nonlinear transition repeatedly, and decodes a prediction only from the final state. The learner selects a reasoning budget of 1, 2, 4, or 8 and receives the actual state trajectory, raw coordinates, norms, prediction, and ground truth. No intermediate natural-language reasoning is generated or displayed.

The observation is intentionally not smoothed into a success story. For the fixed default task, budget 1 predicts `2` instead of `4`; budgets 2 and 4 predict `4`; budget 8 returns to `2`. That failure is useful. It shows that additional applications of a recurrence alter the local computation path, but do not guarantee a better answer in a tiny untrained system. It neither measures token savings nor establishes that latent recurrence is faster, cheaper, or generally superior. The result is a local observation with a separate truth check, not a benchmark.

Two research-oriented modes extend the same inspection discipline. The HRM-inspired local mode is connected to Guan Wang and colleagues’ [*Hierarchical Reasoning Model*](https://arxiv.org/abs/2506.21734). The paper describes coupled high- and low-level recurrent modules operating at different cadences. LatentForge implements a much smaller deterministic educational contrast: low-level state updates every step; high-level state updates at cycle boundaries; output is read from high-level state. The UI returns both numerical trajectories and explicitly marks the mode as a local simplification. It does not reproduce HRM training, adaptive computation, datasets, or benchmark results.

The BDH-CQ-inspired mode asks a different question: what changes when demonstrations construct recurrent memory before a query receives latent workspace updates? Engdahl et al.’s [*BDH-CQ: In-Context Learning with Recurrent Latent Reasoning*](https://arxiv.org/abs/2608.09888) gives a useful published interface: demonstrations update memory `S`; a query and final memory initialize `H₀`; shared updates transform `H`; final `H` is decoded. LatentForge implements that sequence locally with explicit tiny float64 updates. Demonstration count changes the number of real `S` updates. Reasoning budget independently changes the number of post-`H₀` workspace updates. Returned telemetry lets a learner verify those controls affect different stages.

This is not a BDH-CQ reproduction. The paper reports proprietary internal details; LatentForge does not reproduce its trained parameters, dimensions, data, ARC evaluation, candidate ranking, costs, or performance claims. The point is not to simulate a published result. It is to make one source-supported computational relationship inspectable: contextual recurrent memory and query-specific latent work can be separated, then observed.

The evidence labels matter as much as the interface. `LIVE` means the local backend just ran. `PUBLISHED` denotes a statement drawn from a paper. `ILLUSTRATIVE` denotes an explanatory diagram or equation; `SYNTHETIC` is reserved for the explicit arithmetic contract demo. This prevents a beautiful visualization from becoming fabricated evidence.

A later pass asked a harder question about that example: is its pattern — wrong at budget 1, right at 2 and 4, wrong again at 8 — a property of the architecture, or an artifact of one seed? A small local characterization reruns the identical architecture and task across a few additional fixed seeds and records every result, including the ones that never reach the correct answer. The finding is unflattering: across five seeds and four budgets, only three of twenty runs were correct, near chance for this classification. That sharpens, rather than weakens, the point that more recurrent computation is additional computation, not a guarantee of a better answer. It is labeled local and non-benchmark, and does not change the canonical example itself.

The open question is practical and scientific: under what training, architectural, and task conditions do additional latent updates or demonstration-conditioned memory reliably improve a model’s answer? LatentForge does not answer that. It gives learners a transparent way to see why the question requires controlled experiments, independent truth, and honest failure cases.

That framing is also a product decision. A learner can reach the live experiment
quickly, alter one computational variable, and inspect the exact numerical
record behind the displayed verdict. The goal is not to make hidden state seem
mystical. It is to make a bounded computational hypothesis visible enough to
question, repeat, and eventually test on more demanding systems.
